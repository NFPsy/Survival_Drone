# 테스트 로그 분석기

테스터가 게임에서 내려받은 **테스트 로그 파일(.txt)** 을 읽어서, 표로 정리된 **분석 보고서**를 만들어 주는 도구입니다.
예전에는 로그를 사람이 눈으로 읽으며 판 수·클리어율·코어 수지를 세었는데, 이제 명령 한 줄로 같은 일을 합니다.
(테스터가 여러 명이거나 OBT처럼 로그가 많아질수록 이 도구가 도움이 됩니다.)

## 한 줄 사용법

```bash
python analyze_logs.py 로그1.txt 로그2.txt 로그3.txt --out 보고서.md --matches-csv 판목록.csv
```

- `--out 보고서.md` : 분석 결과를 마크다운 파일로 저장합니다. 생략하면 화면에 출력합니다.
- `--matches-csv 판목록.csv` : 모든 판을 한 줄씩 담은 CSV를 만듭니다. 엑셀·구글 시트에서 열어 그래프를 그릴 수 있습니다.
- 같은 테스터가 로그를 여러 번 내보내서 같은 판이 겹쳐도, 합계에는 한 번만 셉니다.
- 파이썬 3.8 이상만 있으면 됩니다. 따로 설치할 것은 없습니다.

## 로그 파일은 어디서 받나요?

게임 로비의 **"테스트 로그"** 창에서 "파일로 저장"(또는 복사)을 누르면 `drone-commander-log-테스터번호-날짜-시각.txt` 같은 파일이 만들어집니다.
테스터가 이 파일을 개인 메시지로 보내면 됩니다.


## 로그 보관 폴더와 폴더 통째 분석 (2026-10-16 추가)

받은 로그 원본은 `tester_logs/` 폴더에 모아 둡니다. 새 로그가 올 때마다 파일을 다시 하나씩 넣지 않고, **폴더를 통째로** 분석합니다.

```bash
python analyze_logs.py tester_logs/cbt
```

- `tester_logs/cbt/` = CBT·OBT 테스터 로그, `tester_logs/dev/` = 개발자 본인 로그.
- 저장소가 공개라서 로그 원본은 깃허브에 올라가지 않습니다(`.gitignore`). 자세한 규칙은 `tester_logs/README.md`.

## OBT 로그만 따로 보기 (2026-10-19 추가)

CBT 로그(빌드 0.2.1)와 OBT 로그(빌드 0.3.0)가 같은 보관 폴더에 쌓이므로, 두 빌드는 규칙·수치가 달라서 합쳐 보면 안 됩니다.
`--build`에 빌드 버전을 주면, 로그 파일 맨 위 머리글의 `빌드:`가 그 버전인 파일만 분석합니다.

```bash
python Tools/LogAnalyzer/analyze_logs.py Tools/LogAnalyzer/tester_logs/cbt --build 0.3.0 --out 보고서.md
```

- 그 버전의 파일이 하나도 없으면 "읽은 파일의 빌드: …"를 알려 주고 멈춥니다.
- 한 파일을 쪼개지는 않습니다. (한 파일 = 한 빌드로 봅니다)

## OBT 설문 응답 분석 (2026-10-19 추가)

구글폼 응답을 구글 시트에서 **CSV로 내려받아**(파일 → 다운로드 → 쉼표로 구분된 값) 넣으면, 질문마다 답을 정리해 줍니다.

```bash
python Tools/LogAnalyzer/analyze_survey.py 응답.csv --out 설문보고서.md
```

| 질문 종류 | 보고서에 나오는 것 |
|---|---|
| 객관식 | 보기별 인원수와 비율 |
| 1~5점 | 평균과 점수별 인원수 |
| 서술형 | 답을 그대로 나열 |
| 플레이 로그 칸 | 붙여 넣은 로그에서 테스터 번호를 찾아 응답 수 표시(파일로 보낸 응답은 "번호 모름") |

- 질문 문구를 읽지 않고 **답의 모양**(점수인지, 짧은 선택지인지, 긴 글인지)만 보고 나누기 때문에, 폼 질문을 고쳐도 그대로 씁니다.
- 응답 CSV에는 개인 답변이 있어서 **저장소 밖**(바탕화면 등)에 저장하세요. 저장소가 공개입니다.
- 설문 응답과 로그를 같은 테스터로 이어 보려면 로그 보고서의 테스터 번호와 설문 보고서의 번호를 눈으로 맞춥니다.

## 보고서에서 볼 수 있는 것

| 구역 | 내용 |
|---|---|
| 한눈에 보기 | 테스터·슬롯마다 판 수, 클리어율, 뽑기 횟수, SSR, 평균 fps, 도중에 나간 판 |
| 스테이지별 | 스테이지마다 판 수, 클리어율, 실패했을 때 평균 생존 시간, 내 전투력이 권장의 몇 %였는지 |
| 전투력 ÷ 권장별 클리어율 | **전투력이 클리어에 얼마나 영향을 주는지**. 하드 스테이지의 체력 배율을 정하는 핵심 숫자입니다 |
| 실패한 판의 생존 시간 분포 | 어느 시간대에 죽는지(예: 1분 30초~2분 30초에 몰리는지) |
| 죽은 원인·받은 피해 | 마지막으로 맞은 적 종류, 적 종류별로 받은 피해 합계 |
| 레벨업 선택 | 이동속도·체력·새 드론·드론 강화를 판당 몇 번 골랐는지, 이동속도를 처음 고른 시간 |
| 성능 | 평균 fps, 100ms 넘게 끊긴 판, 화면 해상도 |
| 슬롯 상세 | 판 목록, 뽑기(SSR이 없을 확률 포함), 락온, 코어 수령, 강화·조각 교환, 상점(데모) 열람·상품별 클릭(OBT 2단계), 코어 수지 점검 |

**코어 수지 점검**은 뽑기·락온·수령 줄의 "남은 코어"가 앞 줄에서 계산한 값과 맞는지 확인합니다. "모든 줄 일치"가 나오면 로그와 게임의 코어 계산이 일관됩니다.

## 조심할 점

1. **기록은 슬롯마다 최근 500줄까지**만 남습니다. 오래 한 슬롯은 앞부분이 잘릴 수 있어서 경고(⚠️)를 띄웁니다. 잘려도 슬롯 맨 위의 "게임이 낸 요약"은 처음부터의 누적 숫자입니다.
2. **판 수가 적으면 클리어율은 참고용**입니다. 테스터 6명이면 판이 수십 개라서 숫자 하나로 결론 내리지 말고 판 수를 같이 봅니다.
3. **권장 전투력 표**(`analyze_logs.py` 위쪽 `RECOMMENDED_POWER`)는 게임의 스테이지 값을 손으로 옮겨 적은 것입니다. 스테이지 값이 바뀌면 여기도 고치세요. 6~8번은 설계 중인 하드 스테이지 값입니다.
4. **빌드 버전이 섞이면 경고**를 띄웁니다. 규칙이나 수치가 바뀐 빌드의 로그는 따로 보세요.
5. **60초 안쪽에 죽은 판**은 조작 실수일 수 있어 판단에서 따로 떼어 보는 것이 좋습니다(보고서가 개수를 알려 줍니다).
6. 그래픽 이름이 `Basic Render Driver`·`SwiftShader` 같은 **소프트웨어 렌더링**이면 fps가 낮은 건 게임 탓이 아니라 환경 탓입니다(보고서가 경고합니다).

## 로그 한 줄의 모양 (참고)

```
10-13 11:09:07 | match | 스테이지=1 결과=실패 생존=545.3초 ... 내전투력=100 ... 사망원인=강한 받은피해=강한126/약한90 성능=평균144fps ...
```

`월-일 시:분:초 | 이벤트 이름 | 키=값 키=값 …` 형식이고, 이벤트는 `match`(판 끝), `match_start`, `match_abandon`(도중 이탈), `pull`(뽑기), `lockon_*`(락온 뽑기), `milestone_claim`·`quest_claim`(코어 수령), `upgrade`, `shard_exchange`, `session_start` 등입니다.
로그 항목이 새로 생기면(예: OBT의 `shop_click`) `analyze_logs.py`에 줄을 추가해서 읽게 하면 됩니다.
